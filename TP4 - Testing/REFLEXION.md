# Reflexión

## 1. ¿Cuántos tests unitarios, de integración y E2E tenés? ¿Por qué esa proporción?

La suite final quedó formada por 19 tests unitarios, 4 tests de integración y 4 tests end-to-end. Hay una mayor cantidad de tests unitarios porque `checkout.py` concentra muchas reglas de negocio, valores límite y combinaciones que pueden comprobarse de forma rápida y aislada. Por ejemplo, se probaron casos como cantidad 10, descuento desde cinco prendas, normalización de talles y vigencia del cupón `EGRESADOS2026`. Los tests de integración son menos porque se enfocan específicamente en comprobar la interacción entre `pedidos.py` y SQLite. Los tests E2E también son menos y se concentran en errores HTTP representativos de R11. Esta distribución permite tener muchas verificaciones rápidas en la base de la pirámide y utilizar los tests más costosos solamente para interacciones entre componentes y recorridos completos del sistema.

## 2. ¿Qué falla de `pedidos.py` no podía encontrarse con un test unitario de `checkout.py`? ¿Por qué?

Una falla que no podía encontrarse mediante tests unitarios de `checkout.py` fue que un pedido inválido podía quedar parcialmente guardado en la base de datos. En el test de integración se envió un carrito inválido y `guardar_pedido` produjo correctamente un `CheckoutError`, pero al consultar SQLite todavía existía un registro en `pedidos`. Esto ocurría porque `pedidos.py` realizaba un `commit` antes de ejecutar completamente el checkout. Un test unitario de `checkout.py` no utiliza SQLite ni controla las transacciones realizadas por `pedidos.py`, por lo que no puede detectar ese efecto lateral. Fue necesario utilizar una base real y consultar su estado luego del error. Este caso muestra por qué los tests de integración encuentran problemas que no pertenecen a una función aislada sino a la interacción entre distintas partes.

## 3. ¿Qué falla de `api.py` estaba en el paso de información entre dos partes del sistema? ¿Qué parte tendría que haberla resuelto?

Una falla clara apareció al pasar un error de negocio desde las capas internas hacia la API HTTP. Al enviar mediante E2E un pedido con talle `XXXL`, `checkout.py` generó un `CheckoutError`, pero la API respondió con HTTP 500 en lugar de devolver 422 con el código `TALLE_INVALIDO`. El problema no era que checkout no detectara el talle, sino que `api.py` capturaba todas las excepciones de manera genérica y las transformaba en errores internos. La responsabilidad de traducir el `CheckoutError` a una respuesta HTTP correcta corresponde a `api.py`, porque es la capa que conoce el protocolo HTTP y sus status codes. El test E2E permitió comprobar la cadena completa desde el request hasta la respuesta recibida por el cliente. De esta manera se detectó una falla en el contrato entre las capas aunque cada parte pudiera funcionar parcialmente por separado.

## 4. ¿Cuál de las fallas que encontraste habría sido la más cara de descubrir en producción? ¿Por qué?

Considero que una de las fallas más costosas en producción habría sido permitir que el cliente enviara su propio precio y que ese valor terminara utilizándose o persistiendo. En el test de integración se envió un buzo con un precio de `1.00` y se comprobó que `pedidos.py` guardaba ese valor en lugar del precio oficial `24999.90`. Esto podría provocar pérdidas económicas reales, ya que un usuario podría manipular directamente los datos enviados al backend. Además, el problema podía pasar desapercibido si solo se probaba el sistema desde una interfaz que siempre enviara precios correctos. La especificación establece justamente que el precio debe provenir siempre del catálogo y cualquier precio recibido debe ignorarse. Detectarlo mediante tests antes de producción evita tanto pérdidas económicas como problemas de integridad de los pedidos almacenados.

## 5. ¿Qué mide la cobertura, qué mide la mutación y qué mide la inyección de fallas? ¿En qué se diferencian?

La cobertura mide qué partes del código fueron ejecutadas durante los tests, por ejemplo líneas y ramas. En nuestra suite llegamos a 97% de cobertura de `checkout.py`, pero una cobertura alta por sí sola no garantiza que las verificaciones sean buenas. El mutation testing modifica intencionalmente operaciones del programa y comprueba si los tests detectan esos cambios; nuestra suite final alcanzó 86,7%, mientras que los tests originales de la IA obtuvieron solamente 58,6%. La inyección de fallas consiste en provocar deliberadamente condiciones incorrectas o excepcionales para observar cómo responde el sistema, por ejemplo enviar JSON roto, un talle inválido o producir un error durante el guardado de un pedido. La cobertura responde principalmente “qué código ejecuté”, mientras que la mutación responde “qué tan sensibles son mis tests a errores en ese código”. La inyección de fallas, en cambio, permite comprobar cómo se comporta el sistema completo ante situaciones anormales y si esas fallas son manejadas de manera controlada.

## 6. Si una IA escribiera tus tests de integración y E2E, ¿qué le faltaría probar? ¿Cómo lo comprobarías?

No confiaría solamente en que una IA genere tests que recorran los caminos principales, porque en este TP los ocho tests originales de IA pasaban y aun así su mutation score fue de solo 58,6%. En integración podría olvidarse de comprobar efectos posteriores al error, como verificar que la base quede realmente vacía después de un `CheckoutError` o abrir una segunda conexión para confirmar que los datos fueron efectivamente persistidos. En E2E también podría limitarse a comprobar que existe una respuesta sin validar el status HTTP y el código de error exactos. Para evaluar los tests generados por IA los compararía primero con cada regla de la especificación y con sus valores límite. También ejecutaría mutation testing cuando sea aplicable y provocaría fallas concretas para verificar que los tests realmente las detecten. Finalmente, revisaría manualmente los límites entre componentes, porque problemas como un `CheckoutError` convertido incorrectamente en HTTP 500 aparecen justamente en esos puntos de integración.
